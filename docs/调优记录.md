# 调优记录：从 0.793 到 0.950 的 MRR

> 这份记录的重点不是「最后数字多好看」，而是**每一次改动都先量、再改、再量**，
> 以及一次「改完发现变差、于是撤掉」的教训。

## 0. 实验设置

- 评估集：`app/eval/datasets/golden_onboarding.jsonl`，35 条（28 single + 2 multi + 2 followup + 3 refusal）
- 本文对比用的是其中 **30 条单轮问答**（排除 2 条 followup 以避免混淆改写能力，排除 3 条拒答题因为无期望文档）
- top_k = 5，指标：Recall@5（是否召回）、MRR（首个正确结果的排名）、nDCG@5（排序质量）
- 环境：离线模式（hashing 向量 + mock 生成），**生成质量不参与本文结论**，只看检索

复现：

```bash
python scripts/evaluate.py --top-k 5              # 全量报告
python scripts/tune.py --top-k 3                  # 参数扫描
```

## 1. 迭代过程

| 版本 | 改动 | Recall@5 | MRR | nDCG@5 | 结论 |
| --- | --- | --- | --- | --- | --- |
| v1 | 基线：纯向量检索（hashing） | 0.900 | **0.793** | 0.825 | 语义通道在降级 embedding 下就不靠谱 |
| v2 | 纯 BM25F（标题 ×5 / 章节 ×3 / 正文 ×1） | **1.000** | **0.961** | 0.973 | 制度类问题的决胜信号是**精确词 + 标题** |
| v3 | 加 RRF 融合 + 词面覆盖度 + MMR 去重（向量一起参与） | 1.000 | 0.928 | 0.948 | **变差**：哈希向量把噪声 chunk 顶到第一 |
| v4 | 检测到 `provider == "hashing"` 时自动关掉向量通道，融合权重自适应 0.85 | 1.000 | **0.950** | 0.960 | 回到最好水平，且真实 embedding 下仍保留混合能力 |
| v5 | 拒答判定重写：BM25 top 分数做 sigmoid + 单块证据覆盖度 | 1.000 | 0.950 | 0.960 | 拒答准确率 **0 → 1.000**，没有误拒正常问题 |
| v6 | 引用校验支持「句号后的标记」归属上一句 | 1.000 | 0.950 | 0.960 | 引用有据率 0 → **0.976**（此前把标记当成空句子） |

> 切块从「固定长度」改成「Markdown 标题切节 + 面包屑」是在 v1 之后、v2 之前做的，
> 但当时没有单独保存那一版的测量结果，所以表里不编数字。它的收益在 v2 的 MRR 里体现了一部分，
> 另一部分体现在「差旅标准」「市内交通」这类短节不再丢失上下文（人工抽查可见）。

## 2. 三次关键发现

### ① 标题权重比想象中重要得多（v1 → v2，MRR +0.168）

单纯 BM25 时，有一类固定失败：

> 问「住宿标准是多少」
> 命中《Skill 开发与上架规范》里的一句话：「当用户询问『这个报销能不能报』『住宿超标了吗』」

这段话是在**举例说明怎么写 description**，但它把「报销」「住宿」两个词都堆在一起了，词频高、长度长，BM25 就打高分。
而正确答案《报销、差旅与采购流程 > 差旅标准》正文里「住宿」只出现两次。

解法：**BM25F 字段加权**——标题命中 ×5、章节命中 ×3。这样「报销」出现在文档标题里的 chunk 稳定胜出。
这不是调参巧合，而是利用了文档结构这个先验：**标题是作者对内容最浓缩的标注**。

### ② 有些改动虽然「理论上更对」，但实测更差，就该撤（v2 → v3 → v4）

v4 加了三样东西：RRF 融合、词面覆盖度、MMR。理论上都对：融合抗单路失效、覆盖度压噪声、MMR 提多样性。
但实测 MRR 从 0.961 掉到 0.928。

排查后原因很具体：hashing 向量是字符 n-gram 哈希，**本质仍是词法匹配但失去了 IDF 加权**，
它给出的 top 候选里有相当比例是「字面像、语义不对」的 chunk。RRF 只看排名不看分数，
于是这些噪声候选和 BM25 的正确候选拿一样的权重，融合后被顶到前面。

于是做了两件事：

1. 在 `HybridRetriever.search` 里判断 `embedder.provider == "hashing"` → **不启用 dense 通道**；
2. 只有词法通道时，覆盖度这个「补丁」会扰动 BM25F 的正确排序，把权重从 0.6 提到 0.85。

> 这不是「混合检索没用」，而是「这一路的输入质量不够格参与投票」。
> 换成真实 embedding（bge-m3 / text-embedding-v3）时，`provider != hashing`，混合路径自动启用。
> **用降级的向量去证明混合检索更好，是自欺欺人。**

### ③ 拒答阈值不能只看一个数（v4 → v5，拒答准确率 0 → 1.0）

最初用「置信度 < 0.18 就拒答」，结果三个本该拒答的问题全部被硬答了。看分布才发现：

| 样本 | BM25 top | 单块证据覆盖度 |
| --- | --- | --- |
| 正常问题（28 条） | 9.2 ~ 34.6 | 0.20 ~ 0.80 |
| 该拒答（3 条） | 4.7 / 6.0 / 7.4 | 0.18 / 0.22 / 0.27 |

两个信号的分布**几乎不重叠**，但用「加权平均的置信度」就被抹平了。于是改成：

```python
confidence = 0.55 * sigmoid((bm25_top - 8) / 3) + 0.25 * evidence + 0.20 * dense_top
足够回答 = confidence >= 0.35 且 (evidence >= 0.20 或 bm25_top >= 9.0)
```

关键是把 BM25 绝对分数用 **sigmoid 以 8 为中心**压到 0~1：这 8 分不是拍的，
是看了上面这张分布表选的决策边界（正常最低 9.2，拒答最高 7.4）。换语料后要重新看这张表。

结果：拒答准确率 3/3，同时 28 条正常问题**一条都没被误拒**（最低 confidence 0.41）。

## 3. 参数扫描（节选）

`python scripts/tune.py --top-k 3` 的部分输出：

| rrf_weight | bm25_b | 标题权重 | Recall@3 | MRR |
| --- | --- | --- | --- | --- |
| 0.5 | 0.30 | 3.0 | 1.000 | 0.922 |
| 0.5 | 0.85 | 5.0 | 1.000 | 0.922 |
| 0.65 | 0.85 | 5.0 | 1.000 | 0.917 |
| 0.80 | 0.85 | 3.0 | 1.000 | 0.880 |
| 0.80 | 0.85 | 5.0 | 1.000 | 0.880 |

两点观察：

1. 在这个语料上，`bm25_b` 和标题权重在扫描范围内几乎不影响结果 —— 说明当前瓶颈不在这些参数，而在 embedding 质量（脚本扫的是同一份 hashing 向量）。
2. `rrf_weight` 越大（越信排名、越不信覆盖度）MRR 越高。这和 ② 的结论一致：**词法通道自己排得挺好，别乱加权。**

> 扫参有个陷阱：这 30 条样本既用来调参又用来报告，容易过拟合。
> 所以最终没有取扫描最优值，而是按「机制解释得通」的原则定 0.6（有向量时）/ 0.85（仅词法时），
> 并在 `docs/评估报告.md` 里如实标注这是离线基线数据。

## 5. 接上真实模型之后：四处必须重做的校准

离线兜底模式（hashing + mock）跑通不代表接真模型就能直接用。配好 `.env` 之后，
真实 embedding 一换，下面四个地方立刻暴雷——**都是跑起来才发现的，不是想出来的**。

### ① 换 embedding → 集合换名 → 新库是空的，但状态文件说「都同步过了」

集合名带模型指纹（`...__openai__text-embedding-v3__1024`），换模型会自动建新集合；
但 `ingest_state.json` 里记着 12 篇文档的哈希，于是 `ingest.py` 判定「全部未变更」→ 全部 skip → **新库永远是空的**，服务起来就是「知识库为空」。

修法（`app/ingest/pipeline.py`）：入库开始时若「库为空但状态非空」，自动改判为全量重建，并打警告。

```python
if known and not reset:
    if int((await self.store.stats()).get("chunks", 0)) == 0:
        log.warning("向量库为空但入库状态非空（通常是换了 embedding 模型），自动改为全量重建")
        force = True
```

### ② 百炼 text-embedding-v3 单次最多 10 条，配置写 16 直接 400

```
400 InvalidParameter: batch size is invalid, it should not be larger than 10.
```

各厂商上限不同（OpenAI 2048、百炼 10、部分自建服务 32），写死在配置里一定会踩。
修法（`app/ingest/embedder.py`）：把「批量条数」当成**可退让参数**——遇到 batch size 这类 400 就把批次折半重试，直到 1 条，
并把折半后的值记住供后续使用。配置里的 16 只是起点，不再是一碰就碎的硬约束。

### ③ MMR 会偷偷调 embedding 接口（评测耗时从 138s 涨到 358s 的原因）

`_mmr` 原本对「没有带 embedding 的候选」（只在 BM25 通道命中的 chunk）调用 `embed_query` 现场补向量。
单次查询多 20~30 次 API 调用，30 条样本 × 多次重复 → 评测从 138s 拉到 358s，线上每次提问也白白多花 1~2 秒和 token。

修法（`app/rag/retriever.py::_mmr`）：有向量就用余弦，没向量就退化成 **字符 2-gram Jaccard** 近似，**永不发起网络请求**。
去重质量几乎无差别（平均不同文档数 3.10 vs 2.53，MRR 不变），但延迟与成本归零。

### ④ 拒答阈值必须重标：旧阈值在真实向量下会「硬答」

用 hashing 向量时，无关问题（食堂几点开饭 / 股票代码）的 `evidence`（单块词面覆盖度）最高 0.22；
换成 bge/text-embedding 之后，语义召回把「词面上有点像」的 chunk 也带了进来，`evidence` 涨到 0.27，
直接越过了原来的 `evidence >= 0.20` 这道闸——3 条该拒的问题有 2 条被硬答，**拒答准确率从 1.000 掉到 0.667**。

看分布才找到仍然干净的判别量：**BM25 top 绝对分**（与 embedding 无关）。

| 样本 | bm25_top | evidence | confidence |
| --- | --- | --- | --- |
| 正常问题（32 条） | 9.2 ~ 34.6 | 0.20 ~ 0.80 | 0.41 ~ 0.90 |
| 该拒答（3 条） | 4.7 / 6.0 / 7.4 | 0.09 / 0.22 / 0.27 | 0.32 / 0.42 / 0.32 |

于是把闸门提成「**必须满足其一**」并参数化：

```env
MIN_CONFIDENCE=0.35
MIN_BM25_ANCHOR=8.5     # 正常最低 9.2，拒绝最高 7.4 → 取中间
MIN_EVIDENCE=0.30       # 抬到 0.30，堵住语义召回带来的虚高覆盖度
```

结果：拒答准确率回到 **1.000**，32 条正常问题**零误拒**（最低 confidence 0.41）。
这也说明一句实话：**这类阈值不存在「一次调好」，换模型就得重标，所以我把它做成了配置项而不是硬编码。**

### 真实模型下的检索对比（同一批 30 条单轮样本，top5）

| 检索方式 | Recall@5 | MRR | nDCG@5 |
| --- | --- | --- | --- |
| 纯向量（text-embedding-v3） | 1.000 | **1.000** | 1.000 |
| 纯 BM25F | 1.000 | 0.961 | 0.973 |
| 混合（最终版） | 1.000 | 0.983 | 0.988 |

三点说明：

1. 换成真 embedding 后，**向量通道从「噪声」变成了「主力」**——这正是第 ② 节「降级时自动关向量」的对称设计：
   现在是 `provider != hashing`，混合路径正常启用；
2. 30 条样本上纯向量已满分，混合 0.983 反而略低：RRF 会让 BM25 的排序参与投票，把个别 dense 已经排对的 top1 稀释掉。
   样本太小，这个差距不具统计意义；
3. 但两路确实**互补**：逐条比 top1 命中，有 2 条是 dense 对而 bm25 错，1 条是 bm25 对而 dense 错（q27「账号没权限找谁审批」）。
   这就是保留混合的理由——真实流量里 OOV 缩写、编号（`L3`、`[[1]]`）靠词法，口语化问法靠语义。

## 6. v8：改写会把该拒的问题「救回来」

接入记忆模块时跑全量测试，`test_unknown_question_refused` 突然红了。查下去不是测试的问题，
而是一个真实漏洞：

| 阶段 | 查询 | bm25_top | evidence | confidence | 判定 |
| --- | --- | --- | --- | --- | --- |
| 首轮 | 公司食堂中午几点开饭？ | 4.7 | 0.22 | 0.33 | 不足（正确） |
| 改写后 | 公司食堂午餐开放时间（供餐时间 就餐时段）？ | **13.4** | 0.15 | 0.65 | 充足（错误） |

`rewrite` 节点为了"救召回"，把口语问题扩写成了带同义词的检索式。
扩写**引入了用户根本没问的词**（"供餐时间""就餐时段"），BM25 分数被抬到 13.4，
直接越过了 `MIN_BM25_ANCHOR=8.5` 这道闸——等于系统给自己发了通行证。

更麻烦的是它**不稳定**：`temperature=0.3`，改写结果每次不同，
所以这个 case 时红时绿，之前几次评估恰好都是 1.000。这种 flaky 漏洞不靠固定测试根本抓不到。

修法（`app/rag/graph.py::grade`）：**改写后必须双条件同时满足**。

```python
strict = round > 0                      # 首轮：词法命中或单块覆盖，二选一即可
passed = (anchor_ok and evidence_ok) if strict else (anchor_ok or evidence_ok)
```

理由：`evidence`（单块覆盖度）衡量"这一块讲的是不是用户问的这件事"，
**塞词能抬高 BM25，但抬不动 evidence**——扩写出来的同义词不会出现在原始片段里。

结果：拒答准确率回到 **1.000**，35 条样本无新增误拒，检索指标不变（MRR 0.984 / nDCG 0.989）。

### 补充：改写温度必须是 0

加了「改写后双条件」之后，同一个问题会出现**今天答得出来、明天被拒答**：
`rewrite` 原本 `temperature=0.3`，改写结果每次不同，`evidence` 在 0.25~0.80 之间跳，
刚好跨过 0.30 这道线。实测「年假可以结转到明年吗」六轮连问，两次跑出两种结果。

改写是**确定性任务**（把口语换成书面检索式），没有多样性需求，温度归零后同一问题判定稳定。
这也说明一件事：只要闸门依赖 LLM 输出，就必须把这个输出钉死。

## 7. 写操作三处「看起来能用、实际会出事」的 bug

做「提议—确认—执行」时踩的三个坑，共同点是**测试都绿着，但线上会出事**。

### ① 身份没有注入到工具：单据挂在「查无此人」名下

`registry.execute(name, args, owner_id=...)` 把 `owner_id` 当成自己的参数，只用来写审计，
**没有传给工具**。写工具拿到的 `owner_id` 是空字符串，于是：

- 工单落库 `owner_id=""`；
- 接口返回 200，`ticket_no` 正常；
- 用户问「我的工单」永远查不到。

修法：身份注入下沉到执行器统一做（`spec.needs_owner` 为真时强制覆盖 `args["owner_id"]`），
缺身份直接拒绝执行。这类错误不该靠每个工具自己记得。

### ② 记忆路由把工单问题截胡了

「我提交的权限工单到哪一步了」同时满足记忆路由的三个条件：提自己 + 问「哪一步」+ 档案里有状态，
于是走到档案作答，答成「入职流程当前在入职培训」——**档案里根本没有工单**。

修法：`memory_covers()` 增加一条排除——出现「工单/申请单/审批/报修/开通/单号」直接 False，
交给工具链路。规则写进 docstring，并配了测试（`test_ticket_question_not_swallowed_by_memory_route`）。

### ③ 协程忘了 await：单元测试全绿，HTTP 500

```text
500 {'code': 'internal_error', 'message': "'coroutine' object has no attribute 'propose'"}
```

`get_actions()` 是 async 的，写成了 `await get_actions().propose(...)`——
先取协程再调方法。单元测试直接注入 service，绕过了这层，所以全绿。

修法是加一条**接口级测试**（`test_api_propose_confirm_roundtrip`）：
真实 HTTP 走一遍提议 → 确认 ×2 → 查工单 → 越权 403。
结论很直接：**服务层的单测替代不了接口冒烟**，这类错只有真发一次请求才现形。

## 8. 编排三个「看起来对、实际会错单」的地方

多步编排跑通只花了一小时，把它改到"敢让人用"又调了三处。共同点：**错的不是流程，是抽取与判定**。

### ① 白名单抽取会把「入口」当成「系统」

语料原句是「申请路径：OA → 权限申请 → 选择系统与角色」。第一版 `_extract_systems()` 只要在白名单里
出现就收，结果把 **OA** 也当成"要开通的系统"——用户照着提交，IT 只会打回。

修法：加一层**句子过滤**，只扫含「勾选 / 包括 / 开通 / 清单」的句子，并把「勾选」之后的内容当作清单。
「OA → 权限申请」这句不含这些词，直接被跳过。

### ② 匹配条件漏了口语说法，模型就自己编参数

用户说「帮我按第一周的清单把开发环境系统**都开一下**」，而匹配器只认「开通 / 开权限 / 申请」——
`开一下` 不匹配，于是掉到单工具路径，模型把系统名填成
**「开发环境（第一周清单所列系统）」**，还生成了待确认单据。

两处都要修，缺一不可：

- 匹配器补上 `开一下 / 都开 / 开个`，让这类委托走剧本（参数从文档取）；
- 给写工具加 `validate` 钩子：系统名含「清单 / 所列 / 相关系统」时**在提议阶段就拒**，
  而不是让用户点了确认才失败。schema 只能校验结构，这种业务判断必须由工具自己声明。

### ③ 抽「规定句」抽到了流程句

问「敏感权限多久到期」，第一版取第一句含「有效期」的——拿到的是
「申请路径：…填写用途与**有效期**…」，答非所问。

修法：给候选句打分——含「默认有效期/到期/回收」加分，含「路径/填写/审批」减分，取最高分。
这不是"更聪明"，而是承认**同一批关键词会命中不同语义的句子**，只能靠上下文词区分。

### 顺带一条设计结论

编排里「提问」和「委托」必须分开：`「第一周要开通哪些系统」` 只答清单，
`「帮我提一下」` 才生成申请。第一版没分，结果用户只是问一句，系统就替他建了待确认单——
虽然没执行，但「我随口一问，你怎么就替我办了」本身就是信任损耗。

## 9. 做端到端评测和多级摘要时，暴露的五个问题

这一轮把「编排」从手测搬进评测集，同时给上下文加了摘要入库。两件事都不难写，
难的是**它们会把之前看不出来的错放大**：手测时你觉得对，一进评测就露馅。

### ① `plan` 里的 `ok` 被当成「有没有数据」，不是「执行成功没」

无导师档案时，「读取入职档案」这一步被标成 `ok=False, detail=无记录`。
前端会画成红色失败条——用户看到的是「系统坏了」，实际是「查了，确实没有」。

修法：`ok` 只表示「这一步执行成功了吗」。没查到数据是**成功的一次查询**，写在 detail 里。
真正失败的只有「没有身份，压根没查」。这条是评测用例 o03 逼出来的：
它断言 `plan` 只有一步且这一步成功，第一版直接红。

### ② 匹配词表要求「系统 / 权限」，用户说的是「开发环境」

「帮我按第一周的清单把开发环境都开一下」——含 `开一下`（上一轮补的），
但不含「系统」也不含「权限」，所以第一个条件过了、第二个条件挂了，掉回文档检索。

修法：第二个条件补 `开发环境 / 环境开通`。
教训和 §8② 是同一个：**匹配词表是按「文档里怎么写」列的，不是按「用户怎么说」列的**。
每次加剧本，都要拿真人问法过一遍，而不是拿自己的措辞过一遍。

### ③ 关键词比对对空格与顺序敏感，指标会因排版抖动

同一批答案，「3 个月」和「3个月」被判成两个结果；模型加不加空格纯属随机。
反生成集上这一条就让覆盖度差了十几个点。

修法：比对前压平空白（`\s` + 全角空格）并统一小写。
这不是放宽标准——人看答案时不会区分空格，评测口径就该和人对齐。

### ④ 反生成把「整句规定」当关键事实，指标虚低

模型生成 `must_contain` 时很爱写整句：
「超出标准的住宿需提前申请特批，出差前提交」。这种句子连人复述都会换措辞，
拿它判分等于要求模型逐字抄。

修法：事实必须是**带数字或英文标识的短事实**（「30 天」「SKILL.md」「ruff」），
且必须在原文里逐字出现。纯中文长短语一律丢弃。
收紧之后反生成集从 0.55 回到 0.93，且报告里剩下的失败是真失败。

### ⑤ 摘要在「增量」上算错了位置，增量永远不触发

`_rolling_summary` 的 `older_end` 第一版写成 `len(history) - len(older)`——
那是 recent 的长度，不是 older 的结束位置。8 条历史时两者恰好相等（4=4），
第二次 12 条时才露馅：应该压 4→8，实际算出 4，`fresh` 恒为空，永远走「复用」。

修法：`older_end = len(older)`（older 就是 history 的前缀）。
这条是单测 `test_incremental_only_summarizes_new_turns` 抓到的——
手动点点界面根本看不出「它每次都在复用旧摘要」，因为答案看起来是对的。

### 顺带：第四个剧本要挡「第三人称」

`travel_standard` 上线后，反生成集里出现「P5 级别的同事去北京能报多少」——
匹配器认了 `P5`，却拿**提问者自己的**档案去套，答成「你是 P5」。
修法：匹配条件排除「同事 / 别人 / 我朋友」。

这条说明一个通用规律：**只要剧本基于「我的」数据作答，就必须先确认主语是「我」**。

## 10. 做答案缓存，两个错都是「跑数字」才暴露的

缓存本身不难写，难的是**判断它到底有没有生效、有没有多生效**。
点界面看不出来——答案一模一样，用户也不会告诉你「这次是缓存的」。

### ① 缓存判断放在工具路由之后，命中还要等 2 秒

第一版把缓存查在 `_tool_answer` 之后，逻辑上很顺：先排掉工具类问题，剩下的才缓存。
实测命中一次 2136ms——比不缓存的 6.5s 好，但远不该这么慢。

原因：`route_tool` 里有 `looks_actionable(question)` 预筛，只要像动作类就会调
`complete_with_tools` 让模型判断意图。「报销单多久内要提交」含「提交」，过了预筛，
于是命中缓存前先白等了一次模型调用。

修法：把缓存判断提到记忆/工具路由**之前**，只在编排之后（编排代表的意图更强）。
安全前提是「工具/记忆/编排的答案从不写缓存」——能命中，就说明这个问题上次是
以纯文档问答结束的，不存在绕开工具的问题。

修完：2136ms → **2ms**。这个数字差就是「缓存位置错了」的代价，而它只在计时时露出来。

### ② 清了 Redis，进程内那层还在命中

`cache_bench.py` 开跑前先清缓存，第一版直接 `redis-cli` 删 `dayone:ans:*`。
结果冷轮 12 题命中 8 题，报告直接失真。

原因：`AnswerCache` 是两层——Redis 和进程内兜底（无 Redis 时也要能跑）。
删 Redis 的键删不掉已经跑起来的进程里那个 dict。

修法：加 `POST /api/cache/clear`，由服务自己把两层一起清，并重置统计。
bench 走这个接口；接口不通才退回删 Redis（并在输出里提示「冷轮可能混入假命中」）。

教训：**带本地兜底的缓存，清理入口必须由持有它的进程提供**，外部删存储永远清不干净。

### ③ 为什么只缓存第一轮（这是设计，不是偷懒）

第一版想用 `standalone_query`（改写后的完整问句）做 key，理论上覆盖面最广。
问题是改写要调模型，缓存命中前先花一次改写，收益立刻被吃掉一半；
更要命的是同一句「那其他城市呢」在不同会话里指向完全不同制度，改写结果不同，
但**原始问句相同**——如果拿原始问句当 key 就会串答案。

结论：第一轮问题语义自包含，直接缓存；追问一律不缓存。命中率略低，但不会错。

### ④ 编排答案必须挡在写入侧

`travel_standard` 的答案取决于提问者的职级。如果它进了缓存，P5 的 600 元/晚
会被另一个 P4 读到——这不是「答案不准」，是数据泄漏。
写入前按 `answer_source` 再挡一层，即使调用方传错 `cacheable=True` 也写不进去。
