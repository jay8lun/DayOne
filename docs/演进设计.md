# 演进设计：从「问答」到「长期运行的助手」

> 本文回答两个问题：**这套东西长期跑下去会怎么坏、以及怎么防**。
> 分三块：记忆（已实现，P0/P1）、上下文管理（设计完成，P2）、工具调用（设计完成，P3）。
>
> 已完成部分见 `app/memory/`，可执行 `python scripts/memory_demo.py` 看完整故事。

---

## 0. 一句话前提

现在的系统能回答「手册里怎么说」，但回答不了三类必然会遇到的问题：

| 问题 | 缺的是什么 |
| --- | --- |
| 「我叫什么、在哪个部门、导师是谁」 | 长期记忆（跨会话、可回溯） |
| 「我的材料交到哪一步了」 | 工作记忆（结构化状态，不是文档） |
| 「上次你说 xxx，现在还算数吗」 | 冲突消解 + 时间轴 |

工业级的分界线不在功能多少，而在**每个记忆决策都可解释、可回滚**。
所以这里的每个设计都带三个字段：`来源原话`、`时间`、`置信度`。

## 1. 记忆分层

| 层 | 存什么 | 存哪 | 生命周期 | 读取方式 |
| --- | --- | --- | --- | --- |
| 短期 | 本会话最近 N 轮原文 | 进程内 `SessionStore`（生产换 Redis） | 会话结束 / TTL 2h | 滑窗 + token 预算拼 prompt |
| 工作记忆 | 流程第几步、材料交了哪些、待补什么 | SQLite `work_items` | 流程结束 | **按 key 精确查**，不做检索 |
| 长期事实 | 部门、导师、工位、账号 | SQLite `memory_facts`（`kind=fact`） | 长期，带有效期 | 槽位精确匹配 + 时间过滤 |
| 长期偏好 | 回答风格、常用系统、习惯 | SQLite `memory_facts`（`kind=preference`） | 慢衰减 | 按时间倒序取最近 k 条 |

**第一原则：能用 SQL 精确查到的，别用向量。**
「流程到第几步」这类问题，向量相似度是纯噪声——这正是把工作记忆放进结构化表的理由。

### 为什么要双时间轴

`event_time`（事情发生的真实时间）和 `record_time`（我们知道的时间）不是一回事。
用户今天说「我上个月搬到杭州」，事件时间在上个月。只存 `created_at`，
之后所有「什么时候变的」都会答错，历史回看也会串。

## 2. 已实现：写入与冲突

### 2.1 数据结构

```sql
memory_facts(
  id, owner_id, subject, predicate, value, kind,      -- kind: fact | preference
  confidence,
  event_time, record_time,                            -- 双时间轴
  valid_from, valid_to,                               -- 时间轴上的有效期
  source_turn, session_id,                            -- 原话与出处，用于「你为什么记得」
  status,                                             -- active|pending|superseded|cold|tombstone
  superseded_by, last_used_at, use_count
)
work_items(owner_id, item_key, step, step_index, materials JSON, updated_at)
audit_log(id, ts, owner_id, action, detail JSON)      -- 所有判断留痕
```

### 2.2 写入闸门：不是每句话都值得记

```text
                 ┌─ 显式指令（"记住…"） ────────────→ confidence=1.0，直接写
用户一句话 ──┬──→├─ 结构化事件（材料提交/流程推进）─→ 事件表，不经 LLM
             │   └─ LLM 异步抽取（回答已返回）─────→ 过置信度闸，否则 pending
             │
             └─ 主链路只负责回答；写记忆全部异步，不拖延迟
```

置信度闸 `MEMORY_CONFIDENCE_MIN=0.7`：低于它只进 `pending`，**不覆盖已有事实**。
宁可多问一句，也不要把用户信息改错——这是与「谁新谁赢」最大的区别。

### 2.3 冲突三分支

同一槽位（`subject + predicate`）出现新值时，按类型分三条路：

| 情形 | 判据 | 处置 |
| --- | --- | --- |
| 事实更新 | 普通事实，事件时间晚于旧值生效时间 | 旧记录 `valid_to = 新事件时间`、`status=superseded`、`superseded_by=新 id`；**不删除** |
| 补录历史 | `mode=backfill` 且事件时间早于旧值生效时间 | 新记录插为一段历史（`valid_to = 旧 valid_from`），**当前事实不变** |
| 纠正旧值 | 事件时间早于旧值生效时间，`mode=auto`（默认） | 旧记录收成零长度区间（作废但保留），新记录从事件时间起生效 → `corrected` |
| 偏好漂移 | `kind=preference` | 保留序列，按时间倒序取最近 k 条，不覆盖 |
| 抽取不可信 | `confidence < 阈值` | 进 `pending`，等用户复述时再定 |

同一值重复上报 = `noop`，只把 `use_count` 加一（该记忆变"更常用"，衰减更慢）。

`mode` 为什么要显式传：这两种意图长得很像，但答错的代价完全不同。
用户说「我上个月就搬了，你记错了」是**纠正**（旧值作废）；
说「我 2019 年在上海工作过」是**补录历史**（现在的事实不变）。
系统猜错就会在「我住哪」这种问题上给出刚被推翻的答案，所以让它必须声明。

### 2.4 遗忘：三级，不物理删除

```text
active ──权重<阈值──→ cold（归档，不参与召回，仍可按时间查回）
                       └──闲置≥N 天──→ tombstone（墓碑，审计可追）
```

权重 = `置信度 × exp(-Δt/半衰期) × (1+ln(1+使用次数)) × 类型系数`

- 偏好有 1.35 倍"耐放"系数：口味不会因为三个月没提就作废；
- **工作记忆不参与衰减**：制度性状态该按流程生命周期硬过期，
  「材料交到哪一步」被慢慢淡忘是事故，不是特性；
- `decay(dry_run=True)` 先试算，看清楚会淘汰谁再执行。

默认参数：半衰期 90 天 / 阈值 0.15 / 冷归档 90 天后立墓碑。
30 天太激进（三个月不聊就把用户住址忘了），这是实测后的取舍。

### 2.5 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/memory/facts` | 写记忆，返回 `action` 说明冲突怎么处理的 |
| GET | `/api/memory/facts?as_of=` | 读记忆；`as_of` 可做时间旅行 |
| GET | `/api/memory/profile` | 拼成可直接进 prompt 的画像 |
| GET | `/api/memory/work` | 流程状态 + 材料清单 |
| POST | `/api/memory/work/step` | 推进流程（幂等、默认挡倒退） |
| POST | `/api/memory/work/material` | 登记材料状态 |
| POST | `/api/memory/decay` | 执行遗忘（支持 dry_run） |
| GET | `/api/memory/audit` | 审计：每次冲突、每次遗忘的判据 |

## 3. 上下文管理（P2，设计完成）

长期跑下去必然撞上窗口上限。四件事难度差很多：

| 能力 | 难度 | 真正的风险 | 设计 |
| --- | --- | --- | --- |
| 旧的压缩、新的保留 | 中 | 压坏最近一轮 → 指代消解崩 | 预算表分层，最近 1~2 轮原文**永不压** |
| 分层摘要入库 | **高** | 摘要漂移，误差逐级累积且不可逆 | 摘要带 turn 回指 + 原文只归档不删 + 摘要存"槽位事实"而非自由文本 |
| 遗忘机制 | 中高 | 权重拍脑袋、误删无法复盘 | 见 2.4，已实现事实层；摘要层同理分级 |
| 闭环检测 | 中 | 做成演示而非度量 | 探针问题反生成 + 统一 clock + 三断言 |

### 3.1 预算表（而不是"截断了事"）

```text
总预算 ≈ 窗口 - 输出预留
├─ 系统提示 + 规则            固定，不参与压缩
├─ 用户画像（memory.profile）  固定，≤ 200 字；超了就摘要
├─ 流程状态（memory.work）     固定，结构化短文本
├─ 检索片段（chunks）          弹性，1~5 条；永不截断（见 §5）
└─ 对话历史                    弹性，最近 2 轮原文 + 更早的摘要
```

### 3.1.1 已实现范围（`app/context/`）

- `budget.py`：token 估算（中文按字、英文按 4 字符）+ 按句读截断；
- `builder.py`：五层预算（系统/画像/流程/资料/历史），**资料永不压缩**，
  历史「最近 2 轮原文 + 更早的摘要」，预算不足时先丢摘要、再丢更早的原文；
- 接入点 `RagService._compose`，响应里带 `context.layers / trace`，接口自证"钱花在哪"；
- **个人状态类问题在检索之前分流**（`memory_covers`）：先判「是不是在问我本人」，
  命中就直接依据档案作答（`answer_source=memory`），不走文档检索——
  否则历史改写会把"我的进度"改写成制度问题，档案被绕过。

这是**启发式路由**，不是语义理解。等 P3 有了工具与意图路由节点，这里换成模型判意图即可。

### 3.2 闭环检测怎么做才算"度量"

- **探针反生成**：从记忆事实生成问句（`city=杭州` → "我住哪？"），隔天换措辞问；
- **时间必须能模拟**：所有时间戳走 `app/memory/clock.py`，测试里 `use_clock(FixedClock(...))` 瞬间跳到三天后；
- **三断言**：
  1. 该记住的——探针命中率；
  2. 该忘的——陈旧/无关记忆的淘汰率（`decay(dry_run=True)` 的召回）；
  3. 不该串的——跨用户污染率（A 的信息出现在 B 的回答里，必须是 0）。

## 4. 工具调用（P3，设计完成）

### 4.1 现状与第一步

`app/rag/llm.py` 目前只有 `complete()` / `stream()`，**没有 `tools` 透传**。
第一步是让封装支持工具调用，且 `MockLLM` 也要能"假装调用"——否则离线兜底与评测链路会断。

### 4.2 该有哪些工具（入职场景，六个够了）

| 工具 | 类型 | 价值 | 风险 |
| --- | --- | --- | --- |
| 查组织架构 / 找人 | 只读 | FAQ 里"找谁审批"直接闭环 | 低 |
| 查流程状态 | 只读 | 直击"材料交到哪了" | 低 |
| 查账号与权限 | 只读 | 省一次求助 | 中（涉及他人信息） |
| 查导师/HRBP 空闲 | 只读 | 中 | 低 |
| 提交工单 / 发起申请 | **写** | 高 | **高，必须二次确认** |
| 检索文档（把 RAG 包成工具） | 只读 | 统一入口 | 低 |

工具数量一多，选择准确率会掉，且每个都要维护 schema + 权限 + 超时。

### 4.3 架构落点

```text
condense ──→ route ──┬── 制度型问题 ──→ retrieve → grade → generate
                     ├── 动作型问题 ──→ tool_call → observe → generate
                     └── 混合型     ──→ retrieve（抽参数）→ tool_call → generate
```

三个新组件：

- **工具注册表**：`name / JSON schema / 只读或写 / 所需权限 / 超时 / 幂等键`。
  这层和 `app/adapters/` 是同一个哲学——**工具也是适配器**，换公司换内部系统只换实现。
- **执行器**：并发、超时熔断、结果裁剪、审计。
- **路由节点**：加在 `condense` 之后。没有它就会出现"用工具回答制度问题"的错配。

### 4.4 四个必须提前定死的事

1. **权限在工具层做，不在 prompt 里做**。新人问别人薪资，靠提示词拦不住。
2. **参数幻觉**：schema 强约束 + 执行前校验；查不到就回问，不允许猜。
3. **写操作三段式**：提议 → 用户确认 → 执行，带幂等键（重复点击不能出两张单）。
4. **结果裁剪**：工具返回 200 行 JSON 会直接撑爆上下文。
   原始 JSON 进日志，进上下文的只有裁剪后的结构化摘要。

### 4.5 与记忆的咬合

- 工具返回的**原始结果不进长期记忆**（瞬时值，存了就是污染）；
- 但**结果的状态**要进工作记忆：「已提交报销单 REQ-2026-111」；
- 调用记录进审计日志——线上排障只有这一个抓手。

## 5. 会打穿现有实现的三个点（务必守住）

1. `app/rag/graph.py::_format_history` 只取最后 4 轮**文本**。
   历史一旦被摘要替换，`condense` 的指代消解会退化 → 摘要里必须保留"最近实体/主题"字段。
2. `app/rag/citations.py` 的引用回验依赖句子与 chunk 原文的词面重叠。
   **压缩只压对话，永不压 chunk**，否则 grounding 会假性下降，看起来像模型变差。
3. `app/rag/sessions.py` 是进程内 dict，重启即丢、多副本不共享。
   长期记忆已外部化到 SQLite；生产换 PG 时只改 `MemoryStore`（接口已按 DAL 抽象）。

## 6. 评估方案

复用现有 `app/eval/` runner，新增两类用例：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 记忆准确率 | 写入后按槽位召回的值与真值一致 | ≥ 0.95 |
| 冲突正确率 | 更新/补录/偏好/低置信四条分支判定正确 | 1.00 |
| 该忘未忘率 | 超期记忆仍在召回的占比 | ≤ 0.05 |
| 误忘率 | 仍有效却被淘汰的占比 | = 0（宁可不忘） |
| 跨用户污染率 | A 的记忆出现在 B 的回答里 | = 0 |
| 探针命中率 | 隔天换措辞提问仍能答对 | ≥ 0.9 |

前四项已可用 `tests/test_memory.py` 的方式断言；后两项需要 P2 的探针集。

## 8. 已知取舍

- **SQLite 而非 PG**：单机演示足够，WAL 并发可用；跨机部署换 `MemoryStore` 实现即可。
- **不做向量化记忆**：事实按槽位精确查更准；语义回忆（"我之前好像提过类似的事"）
  属于 P2 的摘要层，届时再引入向量，且与知识库集合分开，避免污染召回。
- **不做物理删除**：墓碑保留审计能力。真要抹除（合规要求）另做 `purge`，需人工确认。
- **衰减参数是语料/业务相关的**：换场景要重标，所以做成配置项而不是硬编码——
  这与检索阈值 `MIN_BM25_ANCHOR` 的处理方式一致。
