# 技术栈说明：每项技术用在哪、干什么、为什么

> 面向评审/接手的人：不用读完全部代码，看这张地图就能定位。
> 所有路径相对项目根 `05-第五周学习/`。

---

## 一、总览表

| 技术 | 用在哪（文件） | 干什么 | 为什么是它 |
| --- | --- | --- | --- |
| **FastAPI** | `app/main.py`、`app/api/*.py` | Web 框架：路由、依赖注入鉴权、请求校验、OpenAPI 文档、静态资源挂载 | 原生 async（SSE 流式必需）、Pydantic 校验开箱即用、自动生成 `/docs` 方便联调 |
| **Uvicorn** | 启动命令 / Dockerfile CMD | ASGI 服务器，跑 FastAPI | 与 FastAPI 官方配套，支持长连接流式 |
| **Pydantic v2 + pydantic-settings** | `app/config.py`、`app/api/schemas.py` | ① 配置全部来自环境变量并做类型校验；② 接口出入参契约 | 配置写错（比如 chunk_overlap 填负数）启动就报错，而不是跑一半崩 |
| **SSE（Server-Sent Events）** | `app/api/routes_chat.py::chat_stream`、`app/web/static/app.js::streamChat` | 把「检索完成 → 来源列表 → 逐字答案 → 最终指标」分批推给前端 | 比 WebSocket 简单（单向即可）、比轮询省资源、nginx 友好（关掉 buffering 就行） |
| **Docker + docker compose** | `Dockerfile`、`docker-compose.yml` | 一键起服务；向量库与入库状态挂 volume 持久化 | 避免「我机器上能跑」；内网交付只给一个 compose 文件 |
| **RAG（检索增强生成）** | `app/rag/*`、`app/ingest/*` | 整体方案：切块 → 向量化 → 混合检索 → 提示构造 → 生成 → 引用回验 | 业务要求「答案可追溯到原文」，纯大模型做不到 |
| **Embedding** | `app/ingest/embedder.py` | 把 chunk 与 query 编码成向量；支持 OpenAI 兼容接口 + 离线 hashing 兜底 | 公司可能用百炼/bge/自建，统一走 OpenAI 兼容协议最省事 |
| **ChromaDB** | `app/ingest/store.py` | 持久化向量库：按集合存取 chunk、按向量相似度检索 | 嵌入式、零运维、pip 装完就能用；换成 pgvector 只改这一个文件 |
| **BM25F（自实现）** | `app/rag/bm25.py` | 词法检索，标题/章节/正文三档权重 | 制度文档里满是「450 元」「L3」这类精确词，纯向量会糊；不引 `rank_bm25` 是为了支持字段权重且少一个依赖 |
| **RRF（倒数排名融合）** | `app/rag/retriever.py::search` | 融合向量与 BM25 两路排名 | 两路分数量纲不同，加权要调参；RRF 只用排名，换语料不用重调 |
| **MMR（最大边际相关）** | `app/rag/retriever.py::_mmr` | 结果去重，避免 top5 全来自同一段话 | 同一制度常同时出现在「制度文档」和「FAQ」里，不去重会浪费召回位 |
| **LangGraph** | `app/rag/graph.py` | 检索纠错状态机：`condense → retrieve → grade →(rewrite→retrieve)*` | 纠错是**带环的控制流**，用图表达比一堆 if/else 清晰；后续加节点（重排、多路召回）不用改控制流 |
| **LangChain** | 见下方「LangChain 到底用在哪」 | 生态与消息协议兼容；`langgraph` 依赖 `langchain-core` | 没有强行套 LCEL：本项目的 prompt 拼接、检索、引用协议都是自己写的，便于控制和评测 |
| **openai SDK（Async）** | `app/rag/llm.py`、`app/ingest/embedder.py` | 调用 `/v1/chat/completions` 与 `/v1/embeddings`，支持流式 | 国内主流模型（DeepSeek、通义、智谱、硅基流动、vLLM）都兼容这套协议，一套代码全接 |
| **httpx（Async）** | `app/adapters/http_json.py` | 适配器里调外部知识库 HTTP 接口 | 异步、超时/重试/连接池完善，和 FastAPI 同栈 |
| **pdfplumber / python-docx** | `app/adapters/local_dir.py` | 解析 PDF / DOCX 正文（含表格行） | 只在上传/本地目录场景需要，按需 import，不装也不影响主流程 |
| **numpy** | `app/ingest/embedder.py`、`app/rag/retriever.py` | 向量归一化、MMR 的矩阵运算 | 比纯 Python 快一个量级，且是 Chroma 的既有依赖 |
| **orjson** | `app/api/routes_eval.py` | 评估报告 JSON 落盘（中文不转义、快） | 报告体积大，标准 json 慢且默认转义中文 |
| **原生 JS（无框架）** | `app/web/static/app.js` | 聊天界面、SSE 解析、引用角标点击定位高亮 | 内网部署不能依赖 CDN；无构建步骤 = 改完刷新就生效 |
| **pytest** | `tests/` | 27 个单测 + 接口冒烟 | 关键逻辑（切块/BM25/引用/适配器映射）必须有回归保护 |
| **logging（标准库）** | `app/core/logging.py` | 单行结构化日志，docker logs 可 grep | 不引 structlog/loguru，标准库够用 |

## 二、几项技术的「具体落点」

### 1. FastAPI：不止是路由

| 能力 | 代码位置 | 说明 |
| --- | --- | --- |
| `lifespan` 启动钩子 | `app/main.py::lifespan` | 插件加载 → 适配器体检 → 向量库预热 → 空库自动入库。**任一环节失败只告警不崩** |
| 依赖注入鉴权 | `app/api/deps.py::require_api_key` | `SERVICE_API_KEY` 为空则不校验；路由器级 `dependencies=[Depends(...)]` 统一挂 |
| 请求校验 | `app/api/schemas.py` | `question` 长度 1~1000、`top_k` 1~20，非法直接 422，不进业务逻辑 |
| 全局异常处理 | `app/main.py::app_error_handler` | 领域异常 → 结构化 JSON（`code`/`message`），不把堆栈糊给前端 |
| 流式响应 | `StreamingResponse(media_type="text/event-stream")` | 关键响应头 `X-Accel-Buffering: no`，否则 nginx 会把流攒成一坨 |
| 静态站点 | `app.mount("/static", StaticFiles(...))` + `GET /` 返回 index.html | 前后端同域，省掉 CORS 与反向代理配置 |
| 自动文档 | `/docs`（Swagger） | 联调时直接点着测，不用写 Postman 集合 |

### 2. LangGraph：状态机，不是「为了用而用」

```python
# app/rag/graph.py（节选）
graph.add_node("condense", condense)      # 多轮：把「那其他城市呢」补全成完整问题
graph.add_node("retrieve", retrieve)      # 混合检索
graph.add_node("grade", grade)            # 够不够？不够就纠错
graph.add_node("rewrite", rewrite)        # 换个说法再检索
graph.add_conditional_edges("grade", route_after_grade, {"rewrite": "rewrite", "end": END})
```

为什么必须是图：
- `rewrite → retrieve` 是**回边**，普通顺序代码要写成 while 循环，还要手动管重试次数和中间状态；
- `grade` 的判定依据（置信度、证据覆盖度）要留在 state 里，方便打日志、做评估定位；
- 以后加「多路召回（标题检索 / 摘要检索）」只需加节点，不动条件边。

生成阶段**没有**放进图里：SSE 要单独逐字推送，把生成拆出来反而清晰（见 `app/rag/service.py::astream`）。

### 3. LangChain 到底用在哪（说实话）

| 用了 | 怎么用的 |
| --- | --- |
| `langgraph`（构建在 `langchain-core` 之上） | 状态图编排，见 `app/rag/graph.py` |
| `langchain-core` | 作为 langgraph 的运行时依赖存在；本项目**没有**直接用 `Runnable`/LCEL 拼链 |

**没用**（有意为之）的部分：`RecursiveCharacterTextSplitter`（切块要保留标题面包屑，自己写更准）、
`VectorStoreRetriever`（要做 BM25F + RRF，自己写更可控）、`ConversationBufferMemory`（会话要 TTL 和上限，自己写 40 行更简单）。

如果团队后续想统一到 LCEL，替换点是 `app/rag/service.py`：把 `build_answer_messages + llm.stream` 换成
`prompt | model | StrOutputParser` 即可，其余模块不受影响。

### 4. Embedding：一个接口，三种后端

```text
EMBEDDING_PROVIDER = openai  → OpenAI 兼容 /v1/embeddings（百炼 text-embedding-v3 / bge-m3 / text-embedding-3-small）
                   = hashing → 离线字符 n-gram 特征哈希（零依赖、零网络，质量较低）
                   = auto    → 有 key 走 openai，没 key 自动 hashing 并在 /api/health 标 degraded
```

集合名带指纹 `onboarding_kb__{provider}__{model}__{dim}`，换模型自动换库，避免维度不匹配；
入库时若「新集合为空但状态文件说已同步」会自动改判为全量重建（换模型的常见坑）。
批大小可退让：不同厂商单次条数上限不同（百炼 10 / OpenAI 2048），遇到 `batch size` 400 会自动折半重试。
`app/rag/retriever.py` 还会在 `provider == "hashing"` 时**自动关闭向量通道**——因为评估发现哈希向量是噪声源（见调优记录）。

### 5. RAG 的四个工程细节（最容易翻车的地方）

| 细节 | 做法 | 位置 |
| --- | --- | --- |
| 切块保留上下文 | 按 Markdown 标题切节，chunk 存 `heading_path` 面包屑；embedding 用「标题 + 面包屑 + 正文」，展示只用正文 | `app/ingest/chunker.py` |
| 增量更新 | 内容 SHA1 比对；变更文档先删旧 chunk 再写新的；源里删掉的文档同步清理 | `app/ingest/pipeline.py` |
| 引用可核对 | 强制 `[[n]]`、剔除越界编号、逐句词面回验、输出 `grounding_score` | `app/rag/citations.py` |
| 不会就说不会 | `grade` 节点按「置信度 + 单块证据覆盖度」判定，不足直接兜底话术并 `refused=true` | `app/rag/graph.py::grade` |

## 三、如果换技术，改哪里（替换成本）

| 想换的东西 | 改哪里 | 工作量 |
| --- | --- | --- |
| 大模型厂商 | `.env` 改 `LLM_BASE_URL` / `LLM_MODEL` | 0 行代码 |
| Embedding 模型 | `.env` 改 `EMBEDDING_MODEL` / `EMBEDDING_DIM`，重跑 `ingest.py --force` | 0 行代码 |
| 向量库（→ pgvector / Milvus） | `app/ingest/store.py`（实现同样的 6 个方法） | ~120 行 |
| 会话存储（→ Redis） | `app/rag/sessions.py`（kv 接口不变） | ~40 行 |
| 知识库平台 | `app/adapters/` 加一个适配器，或只改 `KB_ADAPTER_CONFIG` | 0~60 行 |
| 前端框架（→ React/Vue） | 只替换 `app/web/static/`，接口不变 | — |
