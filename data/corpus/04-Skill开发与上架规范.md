# Skill 开发与上架规范

「Skill」在云枢指的是**可被智能体调用的能力包**：一个目录 + 一份 `SKILL.md` + 若干脚本/工具，描述「什么时候用、怎么用、注意事项」。公司内部 Skill 市场叫 **SkillHub**，地址 `skillhub.yunshu.internal`。

## Skill 的最小结构

```text
my-skill/
├── SKILL.md          # 必需：元信息 + 使用说明
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：参考资料、模板
└── assets/           # 可选：图片等静态资源
```

`SKILL.md` 的 frontmatter 必须包含：

```yaml
---
name: expense-audit
description: 审核报销单是否符合差旅标准，输入报销明细，输出合规结论与依据条款
version: 1.2.0
owner: 王琳
tags: [财务, 合规]
---
```

## description 怎么写才合格

这是最容易被驳回的地方。description 是模型判断「要不要用这个 Skill」的唯一依据，必须写清楚三件事：

1. **做什么**（能力边界）；
2. **什么时候用**（触发场景，尽量覆盖用户的口语说法）；
3. **不做什么**（避免误触发）。

反例：`description: 报销助手`
正例：`description: 审核差旅报销单是否符合公司标准。当用户询问「这个报销能不能报」「住宿超标了吗」「差旅补贴多少」时使用。不负责提交报销单，提交请走 OA。`

## 开发流程

1. 在 SkillHub 建草稿，拿到 `skill_id`；
2. 本地开发，用 `skillhub-cli dev --id <skill_id>` 挂载调试；
3. 写 3 条以上自测用例（正常 / 边界 / 该拒绝的场景），跑 `skillhub-cli eval`；
4. 提交评审，评审人是所在部门的技术负责人 + 一名跨部门同学；
5. 通过后发布，灰度 7 天，观察调用成功率与用户反馈。

## 三条硬性规范

- **幂等**：同一个请求重复调用结果必须一致，禁止在 Skill 里做「每调用一次就发一条消息」这类副作用。
- **可回滚**：涉及写操作（提交表单、修改数据）必须提供 dry-run 模式。
- **不留密**：Skill 里禁止硬编码任何密钥，统一通过 `secrets.yaml` 引用环境变量。

## 命名规范

- 目录名与 `name` 字段一致，全小写，单词用连字符：`expense-audit`；
- 不要用 `skill1`、`test`、`demo` 这类名字；
- 一个 Skill 只做一件事，超过 3 个职责就拆。

## 常见驳回原因

| 原因 | 占比 | 怎么改 |
| --- | --- | --- |
| description 太模糊 | 42% | 按上面三段式重写 |
| 缺少拒绝场景的用例 | 23% | 补一条「不该触发」的自测 |
| 脚本里有硬编码路径或密钥 | 18% | 改成配置项 + 环境变量 |
| 没有 owner | 10% | 填上负责人的企业微信 |
| 版本号乱写 | 7% | 遵守语义化版本 |

上架后每季度会做一次健康度巡检，连续 90 天零调用且无人维护的 Skill 会被下架归档。
