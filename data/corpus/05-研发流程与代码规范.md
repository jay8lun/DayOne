# 研发流程与代码规范

## 分支模型

我们采用简化的 Git Flow：

- `main`：随时可发布，受保护，禁止直接 push；
- `develop`：日常集成分支；
- `feature/<jira-id>-<简述>`：功能分支，从 develop 切出；
- `hotfix/<jira-id>`：线上紧急修复，从 main 切出，修完同时合回 main 和 develop。

分支存活时间不超过 5 个工作日。超过 3 天的分支必须每天 rebase develop，避免最后合并时冲突爆炸。

## 提交信息规范

格式：`<type>(<scope>): <subject>`

- type：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`
- scope：模块名，如 `retriever`、`api`、`web`
- subject：中文即可，不超过 50 字，不加句号

示例：`fix(retriever): 修复 BM25 空查询导致的除零异常`

不合规的提交会被 commitlint 拦截，CI 直接红。

## 代码评审（MR）规则

1. 单个 MR 改动不超过 400 行（不含自动生成代码和测试数据），超过要拆分；
2. 必须至少 1 名同组同学 approve，核心模块（检索、鉴权、计费）需要 2 名；
3. CI 必须全绿：lint + 单测 + 构建；
4. 评审意见分三级：`[must]` 必须改、`[should]` 建议改、`[nit]` 可有可无。作者可以讨论 `[should]`，`[must]` 必须处理或说明理由；
5. **不要在评审里争论代码风格**，风格交给 ruff/black/pre-commit 自动处理。

## 代码规范要点（Python）

- 统一使用 `ruff` 做 lint 与格式化，行宽 100；
- 类型注解必须写，公共函数必须有 docstring；
- 禁止裸 `except:`，至少 `except Exception` 并记录日志；
- 禁止在循环里做数据库查询或 HTTP 请求（N+1 问题），必须批量；
- 配置一律走环境变量，代码里不出现硬编码的地址、密钥、账号；
- 日志用结构化字段，不要 `print`。

## 测试要求

| 层级 | 覆盖要求 | 谁来写 |
| --- | --- | --- |
| 单元测试 | 核心逻辑分支覆盖 ≥ 70% | 开发 |
| 接口测试 | 所有对外 API 有 happy path + 异常用例 | 开发 |
| 端到端 | 关键链路（问答、入库）各 1 条 | 测试 |

新增功能不带测试的 MR 一律不合并。修 bug 时必须先补一个能复现的失败用例，再修。

## 需求流转

产品提需求 → 需求评审（研发评估工时）→ 排期 → 开发 → 自测 → 提测 → 测试通过 → 发布。

任何「加个小功能，明天上线」的口头需求，必须补一张 Jira 单，否则不排期。这不是流程洁癖，是因为口头需求 90% 会变更。

## 每日站会

每天 10:15，15 分钟以内，每人说三句话：昨天做了什么、今天做什么、有没有阻塞。**不要在会上解决问题**，有问题会后单独拉人。
